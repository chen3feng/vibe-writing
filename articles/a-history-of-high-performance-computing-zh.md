## 一、从"外挂芯片"到集成 FPU：浮点运算的独立战争

### 1.1 8087：CPU 第一块"外挂"

上世纪 80 年代初，Intel 8086/8088 处理器只能做整数运算。要做浮点？不好意思，请自备软件模拟——用几百条整数指令拼出一个浮点乘除法，慢到让人怀疑人生。

**1980 年，Intel 推出了 8087 浮点协处理器**。它是一块独立芯片，插在主板上，和 CPU 并肩工作。8087 在硬件内部定义了 8 个 80 位精度的浮点寄存器（`st(0)`–`st(7)`），以栈的方式操作。这套架构后来被称为 **x87**，统治了 x86 浮点运算长达二十年。

但问题是——它太贵了。在早期的 386/486 时代，FPU 是可选配件。一台电脑如果没有插那块 80387 协处理器，所有的浮点运算全靠操作系统在"非法指令异常"中切到软件模拟，一次除法几百上千个周期。

**直到 1989 年，486DX 才首次将 FPU 集成到 CPU 内部。** 从此，浮点运算才真正从"奢侈品"变成了标配。

### 1.2 Pentium FDIV Bug：一个 4.75 亿美元的"漏网之值"

1994 年，林奇堡学院的数学教授 Thomas Nicely 在用奔腾处理器计算 Brun 常数（一个素数研究问题）时，发现结果总是不对。反复排查之后，他把问题锁定在了 CPU 的浮点除法单元上。

这是计算机史上最著名的硬件 Bug——**Pentium FDIV Bug**。

起因是 Intel 为了追求除法速度，在奔腾中使用了 **SRT 算法**（Sweeney-Robertson-Tocher）。该算法依赖一张硬件内置的查找表（PLA 阵列，约 2048 个单元），但制造过程中有 **5 个本应写入 +2 的条目被错误地填成了 0**。当除法恰好命中这几个条目时，结果从第 4 位有效数字就开始出错。

最经典的测试用例是：4195835 ÷ 3145727。正确结果是 1.333820449...，Bug CPU 算出来 1.333739068...

Intel 起初坚称"普通用户每 27000 年才会遇到一次"，拒绝无条件更换。IBM 随即宣布停售所有奔腾 PC。舆论炸了。

**1995 年 1 月，Intel 宣布计提 4.75 亿美元用于全球换芯。** 折算到今天约 8.68 亿美元。

这次惨剧带来了两项深远变革：一是硬件行业全面引入了**形式化验证（Formal Verification）**——用数学证明替代随机测试来验证芯片逻辑的正确性；二是从 Nehalem 架构（2008 年）开始，Intel 将形式化验证作为芯片设计的默认流程。一个 Bug，改变了整个半导体行业的验证哲学。

## 二、SIMD 军备竞赛：从"一次算一个数"到"一次算一车数"

### 2.1 x87 的末日：为什么栈式 FPU 被抛弃

x87 的致命弱点不在算力，在**编程模型**。

它的 8 个浮点寄存器是**栈式的**（stack-based）。每次运算都在栈顶操作，中间结果需要手动推入弹出。编译器要做极其复杂的寄存器分配和栈深度管理才能生成正确的代码。而相比之下，整数计算用的是平坦的通用寄存器——编译器可以随意安排，极其灵活。

**1999 年，Pentium III 带来了 SSE（Streaming SIMD Extensions）。** 它用 XMM 寄存器（128 位宽）取代了 x87 的栈式模型，同时引入了 **SIMD（单指令多数据）** 能力：一条指令同时处理 4 个单精度浮点数。

x86-64 ABI 的制定者做出了一个决定性决策：在 64 位模式下，**默认用 SSE2 的 XMM 寄存器传递浮点参数**，不再使用 x87 栈。x87 虽然还保留着（为了兼容几十年前的 32 位程序），但在性能领域已经寿终正寝。

### 2.2 向量宽度的疯狂膨胀

SSE 只是一个开始。从那以后，SIMD 的宽度就像被按了快进键：

| 指令集 | 发布年 | 向量宽度 | 代表处理器 | 备注 |
|--------|--------|----------|-----------|------|
| SSE | 1999 | 128 位 | Pentium III | 同时算 4 个 float |
| AVX | 2011 | 256 位 | Sandy Bridge | 同时算 8 个 float |
| AVX-512 | 2016 | 512 位 | Xeon Phi KNL | 同时算 16 个 float |
| ARM NEON | 2011 | 128 位 | Cortex-A 系列 | ARM 阵营的标准向量单元 |
| ARM SVE | 2019 | 128–2048 位 | Fugaku 超算 A64FX | **宽度无关**——同一套代码适配所有宽度 |

AVX-512 的发布方是 Intel 的 Xeon Phi（Knights Landing），一块 72 核的超多核处理器。它在理论上能同时处理 16 个单精度浮点，但对普通用户来说，AVX-512 最出名的是它的副作用——一旦开启，CPU 功耗瞬间飙升，频率反而被迫下降。所以 Intel 在后来的混合架构（大小核）中干脆禁掉了 E 核的 AVX-512 支持，引来了骂声一片。

### 2.3 ARM SVE：Intel 最该警惕的对手

ARM 的 SVE（Scalable Vector Extension）玩了一个更聪明的设计。

传统 SIMD（包括 AVX）指令硬编码了向量宽度：你的代码为 512 位编译，就只能跑在 512 位宽的硬件上。而 SVE 引入了 **Predicate（掩码）** 机制和**向量长度无关**（Vector Length Agnostic）的编程模型——同一段二进制代码，可以在 128 位、256 位甚至 2048 位的硬件上自动适配，不需要重新编译。

这让 SVE 在云原生场景中有巨大优势：AWS Graviton 3/4 上的 SVE2 已经支持 256 位向量，日本的富岳（Fugaku）超算用 512 位 SVE，两者跑的是同一套代码。Intel 后来推出 AVX10 试图模仿 SVE 的"宽度无关"特性，但来得晚了一些。

### 2.4 三操作数：一条被低估的 ISA 设计分水岭

SIMD 的进化不仅是"向量更宽"，还有一个更深层的设计差异，它静默地影响着每一条指令的效率：

**x86 传统上是二操作数架构。** `add a, b` 这条指令的语义是 `a = a + b`——操作数 `a` 既是输入也是输出，被**破坏**了。而 ARM 和 AVX 采用的**三操作数** `add c, a, b` 不破坏任何输入，结果写入独立的 `c`。

这听起像是"少写一个参数"的语法糖差异，但底层影响远比表面大：

- **指令数量膨胀**：为了实现 `c = a + b` 而不破坏 `a`，编译器必须插入 `MOV` 指令先把 `a` 复制到别处。在密集的数学循环中，这些 MOV 会大量占用 CPU 前端解码器的带宽（每周期只能解码 4-6 条指令），让真正的加法乘法排不上队。
- **寄存器重命名的"零开销幻觉"**：现代 CPU 很聪明，对 `MOV xmm1, xmm2` 这样的指令会在寄存器映射表里把两个名字指向同一个物理寄存器，不搬运数据。但 MOV 仍然占用重命名器和重排序缓冲区（ROB）的槽位——就像在文件夹里放快捷方式不花复印时间，但你得花精力写那张标签。
- **乱序执行的潜力被压制**：二操作数因为频繁覆盖寄存器，编译器被迫把中间结果往栈上倒（Register Spilling），产生几百个周期的内存延迟。三操作数下，多个输入互不干扰，CPU 可以同时启动 4-8 组独立计算路径，真正跑满流水线。

Intel 在 2024 年推出的 **APX（Advanced Performance Extensions）** 终于引入了三操作数和翻倍的通用寄存器（16→32 个）。仅靠编译器重编，就能在大量老代码上拿到约 10% 的性能提升——对 x86 这种四十年的老架构来说，这简直是不流血的现代化手术。

### 2.5 SIMD 不是 C/C++ 的专利：Java、C# 和 Go 的向量化之路

提到 SIMD，大多数人想到的是 C/C++ 的手写 intrinsic 或编译器自动向量化。但在高性能计算的版图上，JVM 和 .NET 平台也在悄悄补课——而且他们的打法各有看头。

**Java Vector API（Project Panama）**：Java 长期以来只能依赖 JIT 编译器（C2）的自动向量化——编译器"猜"你想向量化，猜错了就什么也不做。Project Panama 首次给了开发者**显式控制 SIMD** 的能力：通过 `VectorSpecies` 定义向量的抽象形状（长度和类型），`IntVector.fromArray` 加载数据，`va.add(vb)` 直接映射到底层 SIMD 加法指令。代码运行时根据硬件能力自动适配为 AVX2、AVX-512 或 ARM NEON，不需要改任何 Java 代码。不过截至 2026 年，Vector API 仍在孵化阶段。

**C# 是优等生**。C# 从诞生之初就有值类型（`struct`），泛型在运行时是真正展开（Reification）的——`List<int>` 在内存里就是连续的 `int[]`，没有 Java 的装箱问题。加上 **`Span<T>`**（零分配的数组切片视图）、`unsafe` 代码块里的指针操作，以及硬件的 `Avx.Multiply` 等 intrinsics，C# 的 HPC 能力已经直追 C++。今天你可以在 Unity 引擎的 DOTS（Data-Oriented Technology Stack）里看到这些特性在生产环境中的大规模应用。

**Go 走的是另一条路**。Go 编译器对 SIMD 的支持有限，但它的并发模型是独特的 HPC 武器——开 10 万个 goroutine 几乎零开销，这让它在**蒙特卡洛模拟**（并行化百万次独立随机实验）和大规模网格计算上有天然优势。Go 社区的主力数值库 **Gonum** 可以直接链接宿主系统的 OpenBLAS 或 Intel MKL 后端，通过 C 库来弥补汇编层的向量化缺口。

这三种语言的 SIMD 策略恰好代表了三种技术哲学：Java 的"运行时透明适配"，C# 的"给开发者全功率控制"，Go 的"换个维度解决问题"。它们各有所长，但共同指向一个事实——**向量化已经不是 C/C++ 的专属技能了。**

## 三、数学库的古老王朝：BLAS 生态进化史

如果说 SIMD 是硬件层面"算得更快"，那数学库就是软件层面让这些硬件**真正被用起来**。

### 3.1 BLAS：一个定义了世界秩序的接口规范

**BLAS（Basic Linear Algebra Subprograms）** 诞生于 1979 年，最初是 Lawson、Hanson、Kincaid 和 Krogh 为 Fortran 77 设计的线性代数子程序规范。BLAS 的接口天然带有 Fortran 印记——比如矩阵按列优先（Column-Major）存储，至今影响着所有主流实现的底层数据布局和 CBLAS 接口（带 `cblas_` 前缀的 C 语言包装）的设计。

它规定了函数名、参数顺序和语义，但不规定实现方式。它将线性代数运算分为三个级别：

- **Level 1**：向量 × 向量（如 `y = αx + y`）。计算量 O(n)，受限于内存带宽。
- **Level 2**：矩阵 × 向量（如 `y = αAx + βy`）。计算量 O(n²)，部分受限。
- **Level 3**：矩阵 × 矩阵（如 `C = αAB + βC`）。计算量 O(n³)，最容易榨干 CPU 算力，也是优化的核心战场。

### 3.2 从 Reference 到 OpenBLAS：一场三代人接力

理解 BLAS 族谱，能帮你理清半个高性能计算的软件栈：

**Netlib BLAS（Reference BLAS）** 是最早的实现，用 Fortran 编写，没有任何优化——它存在的唯一意义就是当作"标准答案"来验证其他实现的正确性。生产环境没人敢用它，慢得离谱。

**ATLAS（Automatically Tuned Linear Algebra Software）** 开创了"自适应优化"的思路：安装时在你的机器上跑一遍测试，自动选择最优的分块（Tiling）大小。类似于在你家厨房量着锅底尺寸配锅铲。

**GotoBLAS → OpenBLAS** 则走了另一条路：手工为每种 CPU 微架构编写汇编内核。OpenBLAS（基于日本工程师后藤和茂的 GotoBLAS）至今是开源界最流行的 BLAS 实现，它对 Haswell、Zen 3、ARMv8 等几十种架构都有针对性的手工优化。你在 PyTorch 里跑矩阵乘法时，底层很可能就是它。

**Intel MKL（Math Kernel Library）** 是闭源霸主。Intel 亲自操刀，针对自家 CPU 做了别人无法企及的深度优化。它是 PyTorch 在 Intel CPU 上跑得快的核心原因，也是很多商业 HPC 软件的底层标配。

**NVIDIA cuBLAS** 则是 GPU 版的 BLAS——它为 CUDA GPU 实现了整套 BLAS 接口。你在 PyTorch 里写 `torch.matmul` 跑在 GPU 上时，走的就是它。

这套"一个接口，多种实现"的架构如此成功，以至于今天几乎所有深度学习框架的底层，归根结底都是在对 BLAS Level 3 的矩阵乘法做封装和调度。

### 3.3 数学库和编译器怎样协同"作弊"——以 `tanh` 为例

还记得引言里我问的那个问题吗？GPU 怎么算 `tanh`？答案是：**硬件只提供了 `exp`、`rcp`（倒数）和基本算术**，`tanh` 是编译器用公式变形 + 硬件加速拼出来的：

$$\tanh(x) = 1 - \frac{2}{e^{2x} + 1}$$

变形之后整个运算只需要**一次指数**（SFU 的 EX2 指令）、一次加法、一次倒数指令（RCP）、一次乘法和一次减法——全部走硬件快速路径。如果直接套用原始公式 `(e^x - e^{-x})/(e^x + e^{-x})`，需要三次指数和一次长除法，性能远不如这个优化版本。

这正是高性能计算的核心哲学：**最有效率的优化，往往不是让硬件算得更快，而是找到一种方法让硬件少算。**

### 3.4 FFTW：一个"最狂"的库名和一段程序员冷幽默

聊完线性代数，不得不提傅里叶变换。FFT 是信号处理、图像压缩、偏微分方程求解的基石函数。而这个领域最负盛名的开源实现，有一个让人过目不忘的名字：

**FFTW = Fastest Fourier Transform in the West**（西方最快傅里叶变换）。

这个名字不是认真的市场调研产物，而是两位 MIT 开发者（Matteo Frigo 和 Steven G. Johnson）致敬 1960 年代意大利西部片的冷幽默——当年那些电影就叫 "The Greatest [xxx] in the West"（西部最伟大的 xxx）。它既是一种自信的张扬（他们确实写出了当时最快的 FFT），也是一种程序员式的自黑。

更妙的是，这个梗后来被日本人接住了。日本数学家高桥大介（Daisuke Takahashi）开发了一个针对并行架构优化的 FFT 库，名字就叫 **FFTE**（Fastest Fourier Transform in the East，东方最快傅里叶变换）。东西方两大"最快"傅里叶变换，互相致敬。

FFTW 真正的技术革命不在名字，而在架构。传统 FFT 库针对特定硬件死磕代码，换一块 CPU 就不一定是最优了。FFTW 另辟蹊径：它不直接计算，而是先"演习"——根据你当前 CPU 的缓存大小、寄存器数量，测试几十种不同的计算策略（Codelets），选出最快的那个生成"执行计划"（Plan），然后再用这个计划去计算。这种**运行时自适应优化**的思路，后来启发了 ATLAS 和一大批 Auto-Tuning 系统。

当你下一次调用 `numpy.fft` 时——底层大概率就是 FFTW 在跑。

## 四、GPU 的逆袭：从游戏显卡到 AI 世界的钢筋水泥

### 4.1 早期 GPU 不想当"通用计算机"

2000 年代初，GPU 只有一种使命：画三角形。它的流水线被硬编码为"顶点变换 → 光照 → 光栅化 → 像素着色"，每一级的任务固定，不可编程。

转折发生在 2006 年。NVIDIA 推出了 **G80（GeForce 8800）**，采用了**统一着色器架构**（Unified Shader Architecture）——所有处理单元可以灵活切换角色，既能做顶点变换，也能做像素着色。更重要的是，它首次向开发者开放了 C 语言编程能力。

**2007 年，CUDA 1.0 正式发布，GPU 通用计算（GPGPU）时代开启。**

起初人们只敢用它算偏微分方程和线性代数——而且极不情愿，因为要把科学计算问题用 GPU 的术语（纹理、着色器）重新描述一遍，心智负担极大。但第一波吃螃蟹的 HPC 团队很快发现：一块几百美元的消费级显卡，浮点吞吐量远超一块上万美元的服务器 CPU。

### 4.2 Tensor Core：为 AI 而生的"降维打击"

2017 年，NVIDIA 在 Volta 架构（V100）上引入了 **Tensor Core**——一个专门加速矩阵乘累加（GEMM）的硬件单元。

对于深度学习中无处不在的 `C = A × B + C`，Tensor Core 在一个时钟周期内就能完成一个 4×4 矩阵的乘累加操作。相比传统的 FP32 CUDA Core，Tensor Core 在混合精度（FP16 + FP32）下可以提供 **4–8 倍** 的吞吐量。

而 Tensor Core 能这么快的另一个秘密，是它支持的精度越来越"低"：

| 精度 | 位宽 | 场景 |
|------|------|------|
| FP32 | 32 位 | 传统训练和推理 |
| FP16 | 16 位 | 加速训练 |
| BF16 | 16 位（格式不同） | Google TPU 推广，训练稳定性更好 |
| FP8 | 8 位 | H100 引入，推理和部分训练 |
| INT8/INT4 | 8/4 位 | 极致推理加速 |

降低精度 = 更小的数据 = 更高的吞吐 = 更低的功耗。在 AI 推理场景中，从 FP32 切到 INT8，延迟可以降低 3–4 倍，功耗降低一半以上，而精度损失通常不到 0.5%。

### 4.3 AMD 的追赶：CDNA 与 RDNA 的分道扬镳

NVIDIA 在 AI 领域一家独大，但 AMD 没有放弃。它做了一个聪明的决策：将 GPU 架构分为两条线——**RDNA** 专注游戏和消费级图形，**CDNA** 专注数据中心和 HPC。CDNA 2（Instinct MI250X）在 FP64 矩阵乘法上甚至超过了 NVIDIA 同期产品，适合传统科学计算而非 AI 训练。而下一代 MI300X 则直接对标 H100，在内存容量（192GB HBM3）和推理吞吐上正面竞争。

## 五、低延迟 vs 高吞吐：另一条战线的战争

性能优化的战场上，**高吞吐（throughput）** 和 **低延迟（latency）** 往往需要完全不同的打法。

### 5.1 三个共同的敌人

无论是网络、存储还是处理器间通信，延迟都来源于三个元凶：

1. **数据拷贝**：把数据从网卡搬到内核内存，再从内核搬到用户态，每多拷贝一次，延迟就多几十微秒。
2. **上下文切换**：程序需要等系统调用返回、CPU 可能在你的代码和内核之间反复跳跃。
3. **协议栈开销**：TCP/IP 的拥塞控制、校验和、包重排——这些"可靠性保障"在高频交易场景中是赤裸裸的延迟税。

### 5.2 一部"绕过一切"的技术简史

**RDMA（Remote Direct Memory Access）**：让一台服务器的网卡直接读写另一台服务器的内存，CPU 和操作系统完全不参与。配合 RoCE v2 协议，延迟从传统的几十微秒压缩到 **1–3 微秒**。高频交易公司对此如获至宝——一根光纤的距离差异都可能导致下单比别人晚几纳秒，几微秒的改善就是碾压级的竞争优势。

**DPDK（Data Plane Development Kit）**：Intel 开发的网络加速套件，核心思想简单粗暴——用 **轮询（polling）** 取代**中断（interrupt）**。网卡收到包后不再"敲门"通知 CPU，而是等着 CPU 主动来取。这样一来，操作系统内核被完全绕过，延迟的可预测性（消除 jitter）大幅提升。5G 基站的用户面转发，很多跑的就是 DPDK。

**io_uring**：2019 年 Linux 内核 5.1 引入，由 Jens Axboe 设计。它在用户态和内核态之间设立了两个共享的**环形队列**——一个用于提交 I/O 请求（Submission Queue），一个用于获取完成结果（Completion Queue）。**不需要系统调用**就能批量提交和收集 I/O 操作。在此之前，Linux 的最高效异步 I/O 方案（AIO）一直被抱怨"不够异步"，io_uring 终于让文件 I/O 也能达到网络 I/O 级别的低延迟。

**SmartNIC / DPU**：最新的趋势是把整个网络协议栈——包括 TCP、TLS 加密、OVS 虚拟交换——卸载（Offload）到智能网卡上。CPU 不再参与任何网络数据包的处理，专心做业务计算。

### 5.3 互联：当"机箱"成为瓶颈

当一台服务器装不下你的模型时，多机通信就变成了新的延迟源：

- **NVLink 4.0 / NVSwitch**：NVIDIA 的私有互联协议，让数千个 GPU 之间以接近本地显存的延迟通信。这是训练 GPT-4 级别模型的基础设施。
- **CXL（Compute Express Link）3.0**：基于 PCIe 物理层但引入了缓存一致性协议。CPU 可以像访问自己的内存一样访问外部 CXL 设备的内存池，不需要传统 PCIe 那种"握手 → 传输 → 中断"的重型流程。

## 六、未来战场：当"算力"不再是唯一瓶颈

### 6.1 内存墙：算得动，搬不动

过去二十年，CPU 的浮点吞吐量增长了数百倍，但内存带宽只增长了不到十倍。这叫**内存墙（Memory Wall）**。

现在的应对策略是多层次、多尺度的：

- **HBM（High Bandwidth Memory）**：把内存颗粒直接堆叠在处理器旁边，带宽从传统 DDR5 的 300GB/s 飙升到 1TB/s 以上。Intel Xeon Max 和 AMD MI300X 都走这条路。
- **CXL 内存池**：让多台服务器共享同一个外部大内存池。在处理万亿参数大模型的推理时，这可能是唯一可行的方案。

而在这两种硬件方案之外，还有两个更"软"但同样关键的技术：

#### 巨大页面（Huge Pages）：把地址翻译的成本打下来

CPU 访问内存之前，必须把虚拟地址翻译成物理地址。这个翻译结果缓存在 **TLB（Translation Lookaside Buffer）** 里——TLB 是 CPU 内部极贵、极快但**极小**的缓存，通常只有几百个条目。

如果使用标准的 4KB 页面，512 条 TLB 只能覆盖 **2MB** 内存。一次神经网络前向传播的中间张量轻松超过几百 MB，TLB 会全线崩溃——几乎每次内存访问都触发 TLB Miss，CPU 被迫执行 **Page Walk**（逐级查 4 级页表，每次 4 次额外内存访问）。

换成 **2MB 巨大页面**，同样的 512 条 TLB 覆盖 1GB；换成 **1GB 巨大页面**，覆盖 512GB。页表层级也从 4 级缩减到 3 级甚至 2 级。对于长时间占用大量内存的 HPC 和深度学习负载，开启 Huge Pages 通常能带来 5%–15% 的稳定性能提升——这是一个"改一行配置就能拿到的加速"。

#### NUMA 感知：在多路服务器上别"跑错路"

多路服务器的内存是分区的——每个 CPU 插槽有自己的本地内存条。访问**本地**内存和访问**远端**内存（通过 QPI/UPI 总线跨 CPU）的延迟可以相差一倍以上。这种架构叫 **NUMA（Non-Uniform Memory Access，非一致内存访问）**。

Linux 的默认策略叫 **First Touch**：线程第一次**写入**某块内存时，内核才把物理页面分配到该线程所在的 NUMA 节点。这意味着如果你在主线程里初始化了数据再交给工作线程计算，整块数据都会落在主线程所在的节点——所有工作线程都跨节点访问，性能直接腰斩。

正确的做法是**并行初始化**——每个工作线程先"摸"一遍自己的数据区域，让 Linux 把页面分配在正确的节点上。对于更精细的控制，`libnuma` 库允许显式绑定线程到特定节点、在指定节点上分配内存。这不是"玄学优化"——在高频交易和实时推理场景中，NUMA 优化经常是几十微秒差距的来源。

### 6.2 X86 vs ARM：架构之争进入新阶段

Intel 推出了 **APX（Advanced Performance Extensions）**，将 x86 的通用寄存器从 16 个增加到 32 个，并引入三操作数指令（让编译器少写大量 `mov` 指令）。仅靠编译器重编，就能获得约 10% 的性能提升——对 x86 这种"老架构"来说，堪称不流血的升级。

ARM 则在用 **SME（Scalable Matrix Extension）** 反攻 Intel 的 AMX 矩阵加速器。SME 引入了"外积"运算和 Streaming Mode，专门为大规模 GEMM 设计，能让 CPU 在低功耗下完成原本需要 GPU 参与的轻量级训练和推理任务。

### 6.3 云端 AI 芯片：Google TPU 与 Groq LPU

NVIDIA 在 AI 训练市场一枝独秀，但推理市场正在被专用芯片蚕食。两家公司代表了两种截然不同的物理哲学。

**Google TPU（Tensor Processing Unit）**：2015 年秘密部署、2016 年 I/O 大会公开，是全球第一个商用的 AI 专用 ASIC。TPU v1 仅支持推理，28nm 制程，92 TOPS（INT8）——正是它为 AlphaGo 对战李世石提供了底层算力。此后每一代都在翻倍：v2 首次支持训练（2017，AlphaZero）；v3 撑起了 BERT 和 AlphaFold（2018）；v4 用 7nm 工艺和 Mesh 互联将 4096 块芯片捏成一个超算 Pod（2021，>1 EFLOPS）；v5p（2023）单芯片 459 TFLOPS（BF16），Gemini 在其上训练。到 2025 年的第七代 Ironwood（v7），单芯片飙至 4614 TFLOPS（FP8），9216 块芯片组成的 Superpod 聚合算力高达 42.5 EFLOPS。十年间，单芯片算力提升了约 50 倍。

TPU 的竞争壁垒不只是硬件——它深度绑定 TensorFlow/JAX 生态，从编译器（XLA）到训练框架到部署平台（Google Cloud），是一套"买了就别走"的垂直整合。

**Groq LPU（Language Processing Unit）**：如果 TPU 是"越大越强"，Groq 就是"越简越快"。CEO Jonathan Ross 曾是 Google TPU 团队的核心成员。Groq 放弃了 HBM，直接在芯片上堆了 230MB SRAM，内存带宽高达 80 TB/s（H100 的 HBM 带宽约 3 TB/s）。它的架构是确定性的——编译器在编译时就把每条指令的执行时间静态排好，芯片上没有任何分支预测、没有乱序执行、没有缓存未命中。结果：在 Llama 2 7B 推理上达到 750 tokens/s，是 ChatGPT-3.5 的近 20 倍。

但 Groq 的代价也很明显：230MB SRAM 放不下大模型的权重，跑 70B 以上的模型需要多卡串联，经济账就变了。它的最佳战场是**实时交互式推理**——你在地球另一端跟 AI 语音助手对话，延迟必须低于人类感知阈值（~100ms），Groq 的确定性延迟比 GPU 的非确定性调度可靠得多。

### 6.4 端侧 NPU：让笔记本自己跑大模型

云端芯片面向万亿参数，而另一种 AI 芯片在向相反的方向冲刺——把你的笔记本、手机变成独立的 AI 推理设备。

**NPU（Neural Processing Unit）** 不是通用的 CPU，也不是全能的 GPU，而是一颗只做矩阵乘法和卷积的"极简芯片"。没有复杂的控制逻辑，没有图形渲染管线，面积和功耗的每一分钱都花在刀刃上。

Intel Meteor Lake、AMD Phoenix、Apple M4 都内置了 NPU。这些芯片正在让"本地跑 LLM 推理"从概念变成现实——不需要网络，不需要云端 GPU，你的笔记本自己就能跟一个 70 亿参数的小模型对话。

## 七、极致的优雅：Roofline 模型与性能科学

当你在优化一段代码时，怎么知道它的"天花板"在哪？

伯克利实验室的 Samuel Williams 在 2009 年提出了 **Roofline 模型**：绘制一条以"算力峰值"为天花板、以"内存带宽 × 算术强度"为斜率的性能上限曲线。你的程序落在这条曲线上的哪个位置，直接告诉你它是"算不过来了"还是"数据喂不饱"。

运算强度（Arithmetic Intensity，FLOP/Byte）——即每读取一个字节的数据，能做多少次浮点运算——是这个模型的核心指标。矩阵乘法的运算强度极高（O(n³) 计算 ÷ O(n²) 数据 = 随 n 线性增长），所以在 GPU 上跑得很欢；而 `ReLU`（逐元素操作）运算强度极低（几个 FLOP 处理几十个字节），瓶颈不在算力而在带宽——这种操作用 GPU 纯属浪费。

用 Roofline 图分析你的程序，然后把时间花在真正的瓶颈上——这或许是一个工程师从"感觉哪里慢"到"精确知道哪里慢"的分水岭。

## 总结

高性能计算七十年，经历了五个清晰的进化阶段：

1. **硬件独立**（1980s）：浮点运算从软件模拟走向 8087 协处理器，再到片上集成。
2. **SIMD 军备**（1999–2016）：从 128 位 SSE 到 256 位 AVX 到 512 位 AVX-512，向量宽度每 5–7 年翻倍，直到功耗失控。
3. **GPU 登台**（2007–至今）：CUDA 把游戏显卡变成了超级计算机，Tensor Core 又把它变成了 AI 专用引擎。
4. **低延迟革命**（2013–至今）：RDMA、DPDK、io_uring 把通信和 I/O 从"内核交通管制"中解放出来。
5. **异构融合**（2020s–）：CXL 打破内存边界，TPU、Groq LPU 和端侧 NPU 各自切走 AI 芯片的一块蛋糕，ARM 和 x86 在向量化上各自推出 SME 和 APX。

而贯穿始终的，是一条朴素到近乎偏执的信念：**任何让你算得慢的环节，都是可以被工程解决的问题。**

从 Pentium FDIV Bug 那个写漏了 5 个值的查找表，到 NVIDIA H100 里万亿次级别的 Tensor Core 矩阵乘法；从 8087 那块插在主板上的独立芯片，到 M4 处理器里和 CPU 共享总线的 NPU——工程师们用七十年的时间证明了一件事：你永远可以算得更快，只要你对"现有方案"抱持着一种健康的、不可遏制的**不满意**。
