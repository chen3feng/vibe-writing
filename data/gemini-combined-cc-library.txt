## Q1: Java中所有依赖打包在一起的jar叫什么

在Java中，把所有依赖（外部Jar包、配置文件等）和项目本身的代码打包在一起的那个Jar包，通常被称为
Fat JAR
（胖Jar）或者
Uber JAR
。
这两种叫法在行业内最为常见，意思完全相同：
Fat JAR / Uber JAR
：指包含项目自身字节码以及所有运行时所需第三方依赖的自包含（Self-contained）JAR文件。
Shaded JAR
：这是Fat JAR的一种特殊变体。它不仅把依赖打包在一起，还会通过插件（如 Maven Shade Plugin）修改依赖包的包名（Package relocation），以防止不同版本的依赖库发生冲突（即Jar地狱问题）。
💡 常见打包插件
在实际开发中，你通常会通过以下构建工具插件来生成它：
构建工具
常用插件 / 框架
备注
Maven
maven-assembly-plugin
最传统的打包方式，生成
jar-with-dependencies
。
Maven
maven-shade-plugin
支持重命名包名，常用于开发可供他人引用的胖Jar。
Gradle
shadow
插件
Gradle中用来生成 Shadow JAR（等同于 Shaded JAR）的常用插件。
Spring Boot
spring-boot-maven-plugin
Spring Boot 默认打包方式，它采用了一种特殊的双层结构（内嵌
BOOT-INF/lib
），可以直接通过
java -jar
运行。
Export to Sheets
提示：
这种“一包走天下”的方式非常适合微服务部署，因为你不需要在服务器上配置复杂的
CLASSPATH
，直接一行
java -jar xxx.jar
就能跑起来。

## Q2: 对应c++的静态库叫什么好

在 C++ 中，
并没有一个完全等同于 Java "Fat JAR" 的官方标准叫法
，因为 C++ 的编译和链接机制与 Java 有本质区别。
不过，如果非要找一个概念和功能上最对应的词，C++ 中通常称之为
“全静态链接二进制文件”（Fully Statically Linked Binary）
，或者在特定语境下叫
“胖静态库”（Fat Static Library）
。
为了让你更容易理解，我们可以从打包产物（可执行文件）
和
中间依赖（静态库本身）两个维度来对应：
1. 最终运行产物：Fully Statically Linked Binary（全静态链接）
Java 的 Fat JAR 最大的特点是“只要有 JVM，一行命令直接运行，不需要额外装依赖”。
在 C++ 中，最能实现这种体验的是
全静态链接（Fully Static Linking）
。
怎么做
：在编译可执行文件时，通过带上
-static
选项（如
g++ -static main.cpp -o app
），把
libc
、
libstdc++
以及所有第三方
.a
（Linux）或
.lib
（Windows）静态库
全部强行打包进最终的可执行文件中
。
结果
：生成一个体积很大的可执行文件（Binary）。它不依赖系统的任何
.so
或
.dll
，拷贝到同架构的任何机器上都能直接双击运行。
2. 中间依赖产物：Fat Static Library / Monolithic Library（胖静态库/单体库）
如果你是指“把一堆第三方 C++ 静态库（
.a
或
.lib
）合并成一个单独的静态库”给别人用，C++ 里的叫法有：
Fat Static Library（胖静态库）
：业内交流时经常这么叫，意思就是把多个
.a
文件合并成了一个。
Monolithic Library（单体库 / 复合库）
：指将多个子模块或第三方依赖打包在一起的单一库文件。
⚠️ 注意：C++ 合并静态库的坑（区别于 Java）
Java 的 Fat JAR 只是简单的解压和重新压缩（Zip 格式）。但 C++ 的静态库其实只是目标文件（
.o
或
.obj
）的归档包（Archive）。
如果你想把
libA.a
和
libB.a
合并成一个
libFat.a
，不能直接拼接，需要用专门的工具解压再打包：
Linux (AR 工具)
：需要写一个
mri
脚本或者用
ar -x
把所有
.o
解压出来，再用
ar -rcs
重新打包。
Windows (LIB 工具)
：相对简单，可以直接运行
lib.exe /OUT:fat.lib a.lib b.lib
。
总结对比
特性
Java 概念
C++ 对应概念
工具/实现方式
最终分发
Fat JAR
(包含所有依赖，直接运行)
Fully Statically Linked Binary
(全静态链接程序)
g++ -static
库文件合并
Shaded JAR
(合并依赖并解决冲突)
Fat Static Library
(把多个
.a
/
.lib
合并)
Linux 的
ar
脚本 或 Windows 的
lib.exe
Export to Sheets
所以，如果你在和 C++ 程序员沟通：
如果你想表达“不需要装任何环境就能跑的程序”，可以说
“全静态链接的 Binary”
；
如果你想表达“把一堆库打包成了一个库”，可以说
“Fat Static Library”
或者
“合并后的静态库”
。

## Q3: Fat Static Library这个词广为接受吗？

科学地说：
“Fat Static Library” 这个词在 C++ 社区并没有像 Java 的 “Fat JAR” 那样成为一个标准的、人尽皆知的通用术语。
如果你直接对一个 C++ 程序员说这个词，他们大概率能通过字面意思猜到你想表达什么，但在日常开发交流、官方文档或编译工具中，这个词的接受度比较有限。
之所以没有广为接受，主要有以下几个原因：
1. 概念上的“名词冲突”（最核心原因）
在 C++ 和移动端开发（尤其是 iOS/macOS）中，
"Fat Library"（胖库）或者 "Fat Binary"（胖二进制）已经被另一个更重要的概念注册了
：
多架构库（Universal Binary / Fat Binary）
：在苹果生态中，一个
.a
静态库如果同时包含了支持 Intel 芯片（x86_64）和苹果芯片（Apple Silicon / ARM64）的机器码，这个库就被官方和社区称为
Fat Library
。
这种库是通过
lipo
工具把不同架构的库合并而成的。
因此，如果你在 C++ 或 iOS 圈子里说 “Fat Static Library”，大家的第一反应通常是“这是一个支持多 CPU 架构的库”，而不是“这是一个包含了很多第三方依赖的库”。
2. C++ 社区更习惯怎么说？
既然 “Fat Static Library” 容易引起歧义，C++ 程序员在表达“把所有依赖打包在一起的静态库”时，通常会使用以下更地道的词汇：
Combined Static Library（组合/合并静态库）
最朴素也最不容易轻引起歧义的说法。例如：“我们把
libcurl.a
和
libssl.a
合并成了一个
combined static library
。”
Monolithic Library（单体库）
通常用来形容像 OpenCV、Boost 那种，把一堆子模块和第三方依赖融合成一个单一
.a
或
.lib
的大型库。
Self-contained Static Library（自包含静态库）
强调这个静态库本身已经自带了所有需要的底层依赖，使用者不需要再额外链接其他库。
3. 工具链层面的叫法
在构建工具（如 CMake）的生态里，也没有 "Fat" 这个对应选项。
如果是用
CMake
实现这个功能，社区通常称之为
"Bundle Static Libraries"（捆绑静态库）
。在 GitHub 上能找到很多类似
CMakeNinja/BundleStaticLibraries
的开源脚本。
如果是在
Windows (MSVC)
环境下，官方文档和开发者通常直接叫
"Merged Libraries"（合并后的库）
。
总结建议
在和 C++ 同行交流时：
尽量避免孤立使用
“Fat Static Library”
，除非你明确是在玩 Java 的梗（“就像 Java 的 Fat JAR 一样，我们搞个 Fat Static Library”）。
更推荐使用
“Combined Static Library（合并的静态库）”
或
“Self-contained Library（自包含库）”
，这样沟通效率最高，绝对不会产生架构上的误解。

## Q4: Merged，bundle和standalone，加在cc_library前面，哪个好？

在 Google 的
Bazel
或者是
Android 编译系统（Soong/Blueprint）
的语境下（因为
cc_library
是这些构建系统中最核心的组件），选择哪个词作为前缀，取决于你想向团队传达的
核心侧重点
。
这三个词在语义上有微妙的工程差异。以下是对比和推荐：
1. 语义对比
bundle_cc_library
(推荐度：高 ⭐⭐⭐⭐⭐)
语义
：把多个分散的静态库、头文件“捆绑/打包”在一起作为一个整体分发。
工程习惯
：在 CMake、Webpack、iOS 开发中，"Bundle" 都是最标准的用来表示“把一堆依赖打包成一个发布包”的词。它听起来非常像一个
官方的、成体系的构建目标
。
适用场景
：你写了一个脚本或规则，专门用来把主库和第三方库聚合在一起打包给别人用。
standalone_cc_library
(推荐度：中/高 ⭐⭐⭐⭐)
语义
：强调“独立性”，即这个库不依赖任何系统外部的库，拿过去就能用（Self-contained）。
工程习惯
：在工具链（如 Android NDK Standalone Toolchain）中，“Standalone” 专指
自包含、免配置
的产物。
适用场景
：你更想强调它的
易用性
和
独立性
（使用者不需要再额外配置
deps
）。
merged_cc_library
(推荐度：中 ⭐⭐⭐)
语义
：强调“合并的动作”，即把 A、B、C 几个库融合成了一个。
工程习惯
：这个词更像是一个
过程描述
，而不是一个最终的“产品”名称。在大型项目中，它有时会被用作编译中间件的名称。
适用场景
：在构建逻辑内部，比如把几个内部子模块融合成一个过渡库时使用。
2. 哪个更好？（场景推荐）
没有绝对的好坏，只有哪个更地道。你可以根据你的
具体意图
来选：
💡 情况 A：如果是作为通用的自定义 Bazel/Build 规则（Rule）
如果你是在扩展构建系统，写一个可以复用的宏（Macro）或自定义规则，推荐使用
bundle
。
因为这在构建工具链里最专业。
Python
# 示例：看起来非常符合 Bazel 官方命名规范
bundle_cc_library(
    name =
"sdk_release"
,
    srcs = [
":lib_a"
,
":lib_b"
],
)
💡 情况 B：如果是给最终生成的某个特定 Target 命名
如果你是想给某个最终产出的、准备交付给外部团队的 Target 起名字，推荐使用
standalone
。
因为它向使用者传递的信息最直接——“这是一个独立的库，你直接链接它就行”。
Python
# 示例：明确告诉使用者这是一个免配置的独立版本
cc_library(
    name =
"opencv_standalone"
,
    ...
)
总结
想显得
架构更专业、符合构建系统习惯
➡️ 选
bundle_cc_library
。
想强调
产物拿来即用、无外部依赖
➡️ 选
standalone_cc_library
。
尽量不选
merged
，它作为前缀读起来稍微有点像临时变量（像“被合并过的库”）。

## Q5: 最为后缀呢？

如果作为
后缀
（例如
cc_library(name = "xxx_...")
），这三个词的语感和推荐顺序会发生明显的改变。
在起名作为后缀时，C++ 程序员更看重的是“这个库对使用者而言意味着什么”（结果导向），而不是“这个库是怎么做出来的”（过程导向）。
以下是作为后缀时的对比和推荐：
1.
_standalone
(推荐度：最高 ⭐⭐⭐⭐⭐)
语感
：最自然、最地道。
为什么好
：在软件工程中，
_standalone
作为后缀非常普遍（如
foo_standalone.a
）。它明确地告诉使用者：“这是一个
独立版本
，我已经把所有依赖都吞进去了，你拿去直接链接就能用，不需要再操心任何第三方依赖。”
命名示例
：
Python
cc_library(
    name =
"webrtc_standalone"
,
    ...
)
2.
_bundle
(推荐度：中 ⭐⭐⭐)
语感
：略显别扭，更像是一个名词或动词。
为什么不够完美
：
bundle
作为前缀或名词（如 "SDK Bundle"）时很合适，但作为后缀（如
libwebrtc_bundle.a
）时，读起来更像是一个“打包出来的压缩包/文件夹”，而不是一个纯粹的“库文件”。
命名示例
：（可以用，但少见）
Python
cc_library(
    name =
"webrtc_bundle"
,
    ...
)
3.
_merged
(推荐度：低 ⭐⭐)
语感
：带有浓厚的一线开发“临时感”。
为什么不推荐
：
_merged
强调的是“合并”这个动作。它给人的感觉更像是：“为了解决某个编译冲突，我临时把几个库合了一下”。它通常出现在项目的
内部编译中间件
或
临时分支
里，不太适合作为最终交付、长期维护的 Target 名字。
命名示例
：
Python
cc_library(
    name =
"webrtc_merged"
,
# 听起来像是一个临时生成的中间产物
...
)
💡 乱入的黑马：C++ 圈子更常用的另外两个后缀
如果你想让你的
cc_library
名字看起来更加符合顶级 C++ 开源项目的规范，除了
_standalone
之外，你还可以考虑这两个业界标准后缀：
_all
：极其简单粗暴，但被巨型项目广泛接受（例如
GTest / Google Test
）。
GTest 官方编译出的胖静态库就叫
gtest_main.a
和
gtest_with_pthreads.a
等。如果把所有子模块合在一起，社区习惯叫
gtest_all
。
示例：
name = "opencv_all"
_combined
：比
_merged
更正式，强调多个库有机结合成了一个新整体。
示例：
name = "media_deps_combined"
总结建议
作为
后缀
时：
首选
_standalone
：最能直观表达“自包含、无依赖”的意思。
备选
_all
：如果你的项目有一堆子模块（比如
core
,
imgproc
,
video
），把它们全打在一起叫
xxx_all
最符合 C++ 程序员的直觉。

## Q6: ​_combined比_standalone如何

把
_combined
和
_standalone
作为后缀来对比，它们都是非常优秀的工业级命名，但
它们的“世界观”不同，向使用者传达的侧重点有着微妙且关键的差别。
简单来说：
_combined
侧重于“来源”（里面装了啥），而
_standalone
侧重于“结果”（你怎么用它）。
1. 语义与应用场景对比
📊
_combined
（侧重：聚合、多合一）
核心含义
：强调把
好几个性质相同或平级的内部模块/库
合并成了一个大库。
潜台词
：
“我把模块 A、B、C 揉成一个叫 ABC 的库了，方便你一次性引入。”
最适合的场景
：大型框架的子模块合并。
例子
：你的项目有
_audio
、
_video
、
_network
三个组件。如果你把它们打包成一个总库，叫
media_combined
非常地道。它告诉用户：“这里面包含了我们所有的媒体组件”。
缺点
：它
不保证
消除了所有外部依赖。用户可能链接了
media_combined
之后，发现依然报错缺少系统的
libcurl
或
openssl
。
📦
_standalone
（侧重：独立、自包含、无依赖）
核心含义
：强调
开箱即用（Self-contained）
。它不仅合并了内部模块，还把所有第三方的“脏活累活”（外部依赖库）也一起吞进去了。
潜台词
：
“不管里面有什么，反正你链接我就够了，其他什么都不用管。”
最适合的场景
：交付给外部客户、第三方团队的 SDK 产物。
例子
：你的库依赖了
glog
、
protobuf
、
abseil
。你把它们全部强行打包进你自己的库里，起名叫
my_sdk_standalone
。用户拿到后会非常安心，因为他们知道不需要自己再去配一遍 protobuf 了。
2. 总结：哪个更好？
我们可以用一张表格来直观对比它们的适用语境：
维度
_combined
_standalone
视角
开发者视角
（强调内部合并了什么）
使用者视角
（强调外部用起来多简单）
对外承诺
“我不零散，我是合集。”
“我没依赖，开箱即用。”
最配词组
modules_combined
/
deps_combined
sdk_standalone
/
client_standalone
潜规则
后面可能还需要链接别的东西。
后面绝对不需要再链接别的东西。
Export to Sheets
🛠️ 起名终极建议：
如果是给公司内部其他兄弟团队用
：
如果只是为了减少他们的
deps
配置行数，把几个内部子项目合了一下，用
_combined
。
如果是给外部客户、开源社区、或者跨平台分发（如 Android NDK 使用）
：
为了强调“零配置、无死角、全包干”，用
_standalone
。在 C++ 交付领域，
_standalone
的含金量和高级感通常比
_combined
更高。

## Q7: 对于常用的第三方库，打包进去可能会和用户的冲突

你的直觉非常敏锐，这直接戳中了 C++ 静态库打包中
最痛、最经典的一个大坑
：
符号冲突（Symbol Conflict / ODR Violation）
。
在 Java 中，我们有
Shaded JAR
可以通过重命名包名（Package relocation）来完美解决冲突；但在 C++ 中，静态库打包（无论是叫
_combined
还是
_standalone
）如果把常用的第三方库（如
libprotobuf
、
libcrypto
、
libjsoncpp
）直接塞进去，
极其容易和用户自己的同名库发生冲突
，导致编译报错（Multiple definition）或者更可怕的运行时崩溃。
针对你提到的这个致命问题，
_combined
和
_standalone
的起名逻辑和应对策略会发生很有意思的变化：
1. 为什么这时候
_combined
更安全？
如果你只是把
你自己写的、用户不可能拥有的内部子模块
打包在一起，使用
_combined
是最合理的。
潜台词
：
foo_combined
意思是“我合并了我自己的 A、B、C 模块”。
对于第三方常用库
：你
不
打包进去，而是让用户自己在外部链接。这样就不会有冲突。例如，用户自己项目里带了
protobuf
，你的库也依赖
protobuf
，那么大家在最外层共用同一个
protobuf
即可。
2. 如果用了
_standalone
，你就必须“做绝”
如果你决定用
_standalone
这个名字，你就必须对得起它的名字——
实现真正的独立，把冲突的风险在底层彻底抹杀
。
在 C++ 中，为了把第三方库打包进去还不和用户冲突，业界标准的做法不是“直接合并”，而是通过
隐藏符号（Symbol Hiding）
来做物理隔离：
🛠️ 隐藏符号的终极绝招：
Linux / GCC / Clang (
-fvisibility=hidden
)
：
在编译你的静态库时，使用宏或者编译器参数，把塞进去的第三方库的导出符号全部变成
hidden
（隐藏）。这样，这些第三方库的符号就变成了你库内部的隐私，对外部不可见。用户即便在外面链接了一个不同版本的相同第三方库，链接器也不会报错。
Windows (
__declspec(dllexport/dllimport)
)
：
在 Windows 下，通常的做法是
放弃纯静态库
，而是把这堆依赖打包成一个
_standalone
的动态库（DLL）
。DLL 具有天然的符号隔离边界，内部包装的第三方库绝对不会溢出到外面去污染用户。
3. 新的命名灵感：更加小心的语义
如果你想在名字中明确体现“我打包了依赖，但我很安全/我采用了特殊处理”，除了这两个词，开源界还有几种更精细的叫法：
_vendored
（推荐度：高 ⭐⭐⭐⭐）
含义
：指把第三方依赖作为“供应商（Vendor）”的代码直接内置在自己的源码或产物中。
语境
：在 Go、Rust 以及现代 C++ (如 CMake 的
FetchContent
) 中很流行。它告诉用户：“我自带了一套依赖，不用你操心，而且我已经处理好了冲突问题。”
_embedded
（嵌入版）
含义
：强调第三方库是被“内嵌”进去的，通常暗含了已经做了符号隔离。
🚀 最终行动指南
根据你对“冲突”的担忧，名字应该这样选：
如果你妥协了，决定不打包常用第三方库
（只合并自己的模块，第三方库让用户自己配）：
👉 选
_combined
（如
mysdk_combined
），或者干脆叫
_all
。
如果你硬要把常用第三方库打包进去，且你通过编译器技术（如 Visibility 机制）隐藏了它们的符号，保证不冲突
：
👉 坚定地选
_standalone
。因为你真正做到了“独立且安全”。
如果你把第三方库的源码直接抄进来了，并改了命名空间（Namespace）防止冲突
：
👉 选
_vendored
极其地道。

## Q8: Combined能做前缀吗

可以，
combined
完全可以做前缀。
在 C++ 的编译和构建系统（如 Bazel、CMake、Makefile）中，把
combined_
放在前面作为 Target（构建目标）的名字是非常合乎逻辑且通用的做法。
不过，当它从后缀变成前缀时，它的
主谓宾关系
发生了改变，在工程规范上衍生出了两种不同的地道用法：
用法一：
combined_cc_library
—— 作为构建规则/宏（Macro）
如果你是在写一个通用的自定义构建规则，用来把多个库聚合成一个，用作前缀非常完美。
语感
：就像
shared_cc_library
（动态库）或
static_cc_library
（静态库）一样，
combined_cc_library
变成了一个
修饰词
，明确定义了这种库的“物理属性”——这是一个组合库。
Bazel 伪代码示例
：
Python
# 定义一个宏，专门用来合并其他 cc_library
def
combined_cc_library
(
name, deps=[]
):
native.cc_binary(
        name = name,
        linkshared =
False
,
# 或者是特定的静态合并逻辑
deps = deps,
    )
用法二：
combined_xxx
—— 作为特定 Target 的名字
如果你是给某个具体的打包产物命名，把它放前面（如
combined_media_lib
）和放后面（如
media_lib_combined
）在语义上有着微妙的
视觉重心
差异：
放后面（
media_lib_combined
）[更推荐]
：
核心索引是
media_lib
。在 IDE 或日志中按字母排序时，所有和媒体相关的库（如
media_lib_core
、
media_lib_api
、
media_lib_combined
）会排在一起，非常整齐。
放前面（
combined_media_lib
）
：
核心索引变成了
combined
。如果有多个组合库，它们会堆在一起（如
combined_audio
、
combined_video
、
combined_image
）。这通常用于
只读的、最终交付的顶层 Target
。
💡 避坑指南：避免“形容词接形容词”
在 C++ 的
cc_library
生态中，命名有一个潜规则：
尽量避免两个性质相同的形容词连用
。
❌
combined_standalone_cc_library
（组合的独立的库，语义矛盾且啰嗦）
❌
combined_static_cc_library
（组合的静态的库，略显臃肿）
combined_cc_library
（组合的C++库，非常清晰）
总结
combined
做前缀完全没有问题。
如果是用来命名“一种打包规则/机制”
（如
combined_cc_library
），它
比做后缀更好，结构更严谨。
如果是用来命名“具体的库文件”（如
combined_foobar
），它可行，但不如放后面（
foobar_combined
）便于代码库的字母排序管理。

## Q9: 这个规则还得支持排除一些依赖？

支持
排除一些依赖
（通常称为
Exclude
或
Filter
功能）是这种组合库构建规则中
最核心、最刚需
的工程特性。
在实际大厂搬砖中，你把几个库合在一起时，最常遇到的情况就是：
“我想把 A 和 B 合并，但是 A 依赖了
liblog.a
，而用户环境里自带了
liblog.a
，所以我必须在打包时把
liblog.a
剔除掉。”
如果你要在自定义的
combined_cc_library
前缀规则中支持这个功能，从 API 设计和命名的角度来看，有几种非常地道的实现方式：
1. 规则的属性命名（API 设计）
在 Bazel 或类似的自定义构建系统中，这个用于排除的参数通常被命名为
exclude_deps
或
excludes
。
Python
# 极其地道的规则调用方式
combined_cc_library(
    name =
"sdk_combined"
,
    deps = [
"//modules/audio:audio_core"
,
"//modules/video:video_core"
,
"//third_party/glog:glog"
,
    ],
# 核心：支持排除某些经常引起冲突的公共依赖
exclude_deps = [
"//third_party/protobuf:protobuf_lite"
,
# 排除 lite 版，防止用户用 full 版冲突
"@system_libs//:pthread"
,
# 排除系统级线程库
],
)
2. 构建系统底层是如何实现“排除”的？
在 C++ 的世界里，排除依赖不能像 Java 删掉 JAR 包里的一个 class 文件那么简单。底层通常有两种实现策略，取决于你合并的是
源码
还是
二进制链接产物
：
策略 A：拓扑图过滤（Link-time Filtering）—— 最常用
构建系统在收集
deps
时，会生成一个依赖树（Dependency Graph）。
遍历所有
deps
的转导依赖（Transitive Dependencies）。
在最终丢给编译器/链接器进行合并（通过
ar
或
ld -r
）之前，
计算差集
。
从依赖列表中把匹配到
exclude_deps
的
.o
（对象文件）或
.a
（静态库）直接砍掉。
策略 B：符号剥离（Symbol Stripping / Linker Scripts）
如果不从输入端过滤，也可以在输出端通过链接器参数（如 Linux 的
ld --retain-symbols-file
）或者
objcopy
工具，强制把属于被排除库的符号“擦除”掉。
3. 如果支持了 Exclude，名字怎么叫更好？
既然你的规则已经进化到了支持“依赖裁剪”的高级阶段，用
combined
作为前缀依然很合适。但如果你想在命名上进一步区分
普通合并
和
带裁剪的精准合并
，开源界还有两个高端词汇：
dist_cc_library
(Distribution CC Library)
来源
：很多大型项目（如 LLVM/Clang）把这种专门为了分发、裁剪、优化而聚合的库称为
distribution
目标。
语义
：它天生就意味着“这是为了发布而经过精心筛选和修剪的组合库”。
filtered_cc_library
语义
：直接把“过滤/排除”这个特性写在脸上。不过通常作为内部逻辑名，对外做成
combined_cc_library
的一个参数（即上面代码里的
exclude_deps
）更整洁。
总结
支持 Exclude 是完全正确且必须的工程方向。在设计时：
宏/规则名：继续使用
combined_cc_library
作为前缀。
参数名：定义一个
exclude_deps
（列表类型），这最符合现代构建系统（如 Gradle、Bazel）用户的直觉。

## Q10: 还需要支持导出头文件吗？

是的，绝对需要！而且在 C++ 的工程实践中，“导出头文件”的难度和重要性，甚至超过了把
.a
静态库合在一起。
在 Java 中，字节码（
.class
）和元数据都封装在 JAR 包里，只要引入了 Fat JAR，类和方法就能直接被调用。
但在 C++ 中，
光给用户一个合并后的二进制库（
.a
/
.lib
）是完全没法用的，用户必须有对应的头文件（
.h
/
.hpp
）才能通过编译。
因此，一个成熟的
combined_cc_library
规则，必须配套支持
头文件的收集与导出（Header Bundling）
。
1. 为什么“导出头文件”是个技术活？（避免头文件污染）
在大型项目里，各个子模块的头文件通常是散落各处的。如果你直接把它们原封不动地打包给用户，会遇到两个致命问题：
内部私有头文件外泄
：有些头文件（比如
internal_helper.h
）只是你内部实现的细节，根本不想暴露给用户。
路径嵌套太深
：你内部的引用可能是
#include "modules/audio/src/impl/codec.h"
，如果直接丢给用户，用户配置
include_paths
会痛苦到抓狂。
2. 业界标准做法：头文件“大一统”（Header Flattening）
为了配合
combined_cc_library
，构建系统通常需要做两件事：
🟢 做法 A：声明公有 API（Public Headers）
规则必须有一个参数（通常叫
hdrs
或
public_hdrs
），明确指定哪些头文件是需要暴露给用户的。
Python
combined_cc_library(
    name =
"sdk_combined"
,
    deps = [
":audio"
,
":video"
],
    exclude_deps = [
"//third_party/glog"
],
# 核心：明确哪些是吐给用户的接口头文件
hdrs = [
"//modules/interface:sdk_api.h"
,
"//modules/interface:types.h"
,
    ],
)
🟢 做法 B：头文件扁平化（Flattening / Sandboxing）
构建系统在打包时，会把这些指定的
hdrs
统一复制到一个干净的输出目录（例如
include/
）。
内部所有私有的、被
exclude_deps
剔除的依赖所对应的头文件，
一律不复制
。
这样用户拿到后，目录结构非常清爽，只需要在他们的项目里加上
-I/path/to/sdk/include
，然后
#include <sdk_api.h>
即可。
3. 更高级的玩法：伞形头文件（Umbrella Header）
如果合并的模块实在太多（比如有 50 个公开的
.h
文件），让用户一个个去
#include
体验非常差。
通常
combined_cc_library
会在打包时，
动态自动生成一个“总领头文件”
（也就是大名鼎鼎的
Umbrella Header
）。
这个文件的名字通常和库名一致，比如
sdk_combined.h
。
它的内容非常简单，就是把你导出的所有公开头文件全部
#include
一遍：
C++
// sdk_combined.h 自动生成
#
pragma
once
#
include
"sdk_api.h"
#
include
"types.h"
#
include
"audio_config.h"
用户以后用你的库，只需要一行
#include <sdk_combined.h>
，就能解锁整个 SDK 的所有功能。像大名鼎鼎的
OpenCV
(
#include <opencv2/opencv.hpp>
) 和
Vulkan SDK
就是这么做的。
总结
没有头文件导出的
combined_cc_library
是不完整的。一个好用的 C++ 打包规则，最终产出的目录结构应该像这样：
Plaintext
outputs/
├── lib/
│   └── libsdk_combined.a       # 精简、去重、排除了冲突依赖的“胖静态库”
└── include/
    ├── sdk_combined.h          # 自动生成的伞形头文件（Umbrella Header）
    ├── sdk_api.h               # 你指定的公开接口
    └── types.h                 # 你指定的公开接口

## Q11: Bazel上有类似的实践吗？

在 Bazel 的原生规则中，官方并没有直接提供一个名为
combined_cc_library
的内置规则。这主要是因为 Bazel 的核心哲学是“细粒度依赖（Fine-grained dependencies）”，它更鼓励你在整个 monorepo 中直接依赖具体的
cc_library
目标，而不是频繁地在中间阶段做二进制合并。
但是，
在实际的工业级大厂（尤其是需要对外发布 C++ SDK 的团队）中，类似的自定义实践非常普遍，而且几乎是刚需。
业界在 Bazel 上实现这种“带依赖排除、带头文件导出”的组合库，主要有以下三种主流实践方式：
实践一：使用
cc_binary
强行逆向输出静态库（最经典的 Hacking 技巧）
这是 Bazel 社区流传最广的一个“黑魔法”。虽然
cc_binary
默认是用来生成可执行文件或动态库（
.so
/
.dll
）的，但你可以通过开启
linkshared = True
或调整参数，配合特定的配置来强行让它吐出一个包含所有
deps
的归档文件。
不过这种方式对“排除依赖（Exclude）”的支持比较生硬，往往需要通过底层的
copts
或链接器脚本（Linker Script）来肉搏。
实践二：大厂最爱，自定义 Starlark 规则 / 宏（Macro）
为了优雅地支持你前面提到的
exclude_deps
和头文件导出，绝大多数团队（如 Google 内部的一些开源项目、自动驾驶公司等）都会编写自定义的 Starlark 规则。
它的底层逻辑通常是：利用 Bazel 的
CcInfo
提供者（Provider）去搜集所有依赖的
.o
（对象文件）和头文件，然后通过
Action
调用系统的
ar
（Linux）或
lib.exe
（Windows）进行打包。
一个典型的 Bazel 社区级开源实现是：
@rules_cc
的扩展或类似
bazel-distribution
的第三方库
。它的核心逻辑如下：
Python
# 自定义宏的伪代码实现
def
combined_cc_library
(
name, deps = [], exclude_deps = [], public_hdrs = []
):
# 1. 过滤依赖：利用 Starlark 脚本计算 deps 和 exclude_deps 的差集
filtered_deps = [d
for
d
in
deps
if
d
not
in
exclude_deps]
# 2. 收集并打包二进制
# 内部会触发一个 genrule 或自定义 action，调用 'ar' 将 filtered_deps 的 .o 文件融合成一个 .a
# 3. 头文件扁平化收集 (Header Flattening)
# 触发一个 filegroup 或 genrule，把 public_hdrs 复制到特定的公共 include 目录下
native.genrule(
        name = name +
"_hdr_collection"
,
        srcs = public_hdrs,
        outs = [
"include/"
+ h.split(
"/"
)[-
1
]
for
h
in
public_hdrs],
        cmd =
"cp $(SRCS) $(@D)/include/"
,
    )
实践三：使用第三方成熟的 Bazel 发布插件（推荐）
如果你不想自己从零手写复杂的 Starlark 规则去处理各种平台的
ar
命令兼容性，Bazel 生态里有一些现成的开源规则库专门解决这个问题：
1.
bazel_rules_distribution
这是专门为 Bazel 设计的用于“打包发布”的规则集。它不仅支持把多个
cc_library
合并，还支持：
明确指定哪些是公开头文件。
自动剥离（Strip）不需要的符号。
排除指定的第三方依赖。
2. Android 源码（AOSP）中的
cc_library_shared
/
cc_library_static
实践
如果你看过 Android 系统的 Bazel 迁移（Blueprint/Soong 转换过来的规则），他们有非常庞大的复合库打包需求。他们内部通过大量的自定义 Action，实现了在合并
.a
的同时，自动生成一个统一的元数据文件和扁平化头文件目录。
💡 一个真实的 Bazel 打包产物长什么样？
在 Bazel 中，当你运行
bazel build //my_sdk:combined_sdk
后，它通常会在
bazel-out/
下为你生成一个干净的
tar
包。解压后就是标准的 C++ SDK 结构：
Plaintext
bazel-bin/my_sdk/combined_sdk.tar
├── libmy_sdk_combined.a          # 过滤掉 exclude_deps 后的胖静态库
└── include/                      # 导出的公开头文件沙盒
    ├── my_sdk.h                  # 伞形头文件（Umbrella Header）
    └── public_api.h
总结
在 Bazel 上：
官方没有现成的
，因为这违反了 Bazel “尽量不重复打包中间件”的初衷。
民间和各大厂方案高度统一
：一律通过自定义 Starlark 宏，对外暴露
combined_cc_library(name, deps, exclude_deps, hdrs)
的接口，底层用
genrule
或 Action 调用
ar
和
cp
来实现。如果你正在设计这个规则，这条路完全是行业标准的正确方向。

## Q12: 还要有哪些功能

一个真正达到
工业级、能够闭环分发
的
combined_cc_library
构建规则，除了具备合并静态库、排除依赖（Exclude）和导出头文件（Flatten Headers）之外，还需要具备以下几个
隐藏的硬核功能
。
在实际生产环境中，缺乏这些功能会导致用户在使用你的组合库时，依然频繁报错或链接失败。
4. 传递性编译参数的合并与过滤（Exported Flags / Defines）
C++ 库不仅仅是代码和头文件，它们往往还绑定了特定的编译宏（Defines）或包含路径（Include Paths）。
功能需求
：当 A 库和 B 库合并时，它们原有的
copts
或
defines
（例如
-DENABLE_DEBUG=1
）必须能够自动传递并合并到最终的
combined_cc_library
中。
过滤需求
：被你
exclude_deps
剔除的库，其绑定的宏和参数也
必须同步被剔除
，否则会导致最终用户编译时带上了错误的宏，引发未定义行为。
5. 系统级依赖的自动提取与声明（System Link Flags）
你的库可能排除了一些第三方库，但有些
系统基础库
（如
-lpthread
、
-lm
、
-ldl
）你是无法打包进静态库的，用户必须在最外层链接它们。
功能需求
：规则需要有一个
linkopts
属性，能够
自动收集
所有底层依赖所需要的系统链接参数，并在最终的元数据（如
pkg-config
）中声明。
用户体验
：这样用户链接你的组合库时，构建系统能自动补上
-lpthread
，不需要用户看报错去盲猜。
6. 同时生成并打包动态库（Shared Library Support）
在 C++ 交付中，只提供静态库是不够的（可能存在前面提到的符号冲突、代码体积过大问题）。
功能需求
：你的
combined_cc_library
最好能够根据一个参数（如
linkshared = True/False
），一键切换输出静态库（
.a
/
.lib
）还是动态库（
.so
/
.dll
）。
Windows 平台的刚需
：在 Windows 下，如果生成动态库，规则还必须自动处理
__declspec(dllexport)
的符号导出逻辑，并同时产出
.dll
（动态库）和
.lib
（导入库）。
7. 符号冲突的终极防御：符号重命名/隐藏（Symbol Renaming / Hiding）
这是最高阶也是最能体现技术功底的功能。即使你用了 Exclude，有些你
不得不打包进去
的公共库（比如某个特定版本的
libjpeg
）依然可能和用户冲突。
功能需求
：规则需要支持符号修饰（Symbol Mangling）或局部链接（Partial Linking）。
技术实现
：
在 Linux 下，在合并
.o
文件时，利用
objcopy --localize-hidden
，把你打包进去的第三方符号全部变成
局部符号（Local Symbols）
。
这样，外部用户即便用
nm -D libyour_combined.a
查看，也只能看到你导出的公开 API，第三方库的符号在物理上被完全隐藏，彻底免疫符号冲突。
8. 自动生成现代元数据文件（CMake Config / pkg-config）
现在没有人在引入第三方库时还在手写编译器链接命令了，大家都在用 CMake 的
find_package()
或者
pkg-config
。
功能需求
：你的构建规则在吐出
.a
和
.h
的同时，应该
自动生成
配套的
.pc
文件（pkg-config）或
MySDKConfig.cmake
文件。
自动生成的文件内容示例（
mysdk.pc
）
：
Plaintext
Name: MySDK
Description: Combined C++ SDK
Version: 1.0.0
Cflags: -I${includedir} -DMY_SDK_BUILT_IN=1
Libs: -L${libdir} -lmysdk_combined -lpthread -lm
有了这个文件，用户只需要在他们的 CMake 里写一行
find_package(MySDK REQUIRED)
，你的头文件路径、静态库路径、系统依赖（
-lpthread
）就全部一次性自动配好了。
总结：完美的
combined_cc_library
终极形态
一个无懈可击的
combined_cc_library
宏，其全功能的伪代码定义应该长这样：
Python

"universal_sdk"

    deps = [
"//src:core"
,
"//third_party:jsoncpp"
],
    exclude_deps = [

具备了
依赖排除、头文件扁平化、系统依赖传递、符号隐藏、元数据生成

## Q13: Objcopy --localize-hidden如何控制保留的公开符号的

在 Linux C++ 开发中，
objcopy --localize-hidden
是一个非常高级且好用的“黑科技”命令。它的核心作用是：
把所有被标记为“隐藏（Hidden）”的全局符号，批量降级为“局部符号（Local）”，从而让它们在静态库外部彻底不可见。
但这里的关键在于：
它自己其实不负责挑选谁保留、谁隐藏。它是一个“执行者”，必须配合编译器（GCC/Clang）的前期标记来协同工作。
下面是它的底层运作机制和控制公开符号的标准工作流：
第一步：代码层面，用属性控制可见性（最底层控制）
在 C++ 代码中，你需要明确告诉编译器，哪些是你想导出的“公开符号”，哪些是内部的“隐私符号”。这通过
__attribute__((visibility("...")))
来控制。
C++
// api.h —— 这是你想保留的公开符号
#
define
SDK_EXPORT __attribute__((visibility(
"default"
)))
class
SDK_EXPORT
MyPublicAPI
{
public
:
void
doSomething
()
;
// 外部可见
};
// internal.h —— 这是你不想暴露的内部符号（或者引入的第三方常用库）
#
define
SDK_LOCAL __attribute__((visibility(
"hidden"
)))
class
SDK_LOCAL
InternalHelper
{
public
:
void
secretMethod
()
;
// 隐藏符号
};
default
（默认）
：意味着这个符号是公开的，链接器在合并时要保留它。
hidden
（隐藏）
：意味着这个符号是内部的，虽然在编译成
.o
时它是全局的（方便内部其他
.o
链接），但最终不应该漏给外面的用户。
💡 大厂偷懒秘籍：默认全部隐藏
如果第三方库的源码你没法改，不能一个个去加
SDK_LOCAL
怎么办？
你可以在编译这个静态库时，给 GCC/Clang 加上一个全局参数：
-fvisibility=hidden
。
这样，所有没有显式加
SDK_EXPORT
的符号，
默认全都会被标记为
hidden
。
第二步：观察
objcopy
处理前的符号状态
当你把这些
.cpp
编译并用
ar
打包成一个未处理的静态库
libbefore.a
时，如果你用
nm
命令去查看它的符号表，你会发现
公开符号和隐藏符号都是全局的（Global）
：
Bash
nm libbefore.a
输出可能长这样：
Plaintext
0000000000000000 T _ZN11MyPublicAPI11doSomethingEv   # T 代表 Global Code (公开)
0000000000000020 t _ZN14InternalHelper12secretMethodEv # t 或者是带有特定隐藏标记的 Global
在 ELF 文件格式的底层，那些被标记为
hidden
的符号，其
STV_HIDDEN
属性会被激活。
这就是给
objcopy
留下的“记号”。
第三步：大招降维打击：
objcopy --localize-hidden
现在，你对这个静态库执行这条命令：
Bash
objcopy --localize-hidden libbefore.a libsdk_combined.a
它的内部控制逻辑非常简单粗暴：
objcopy
扫描
libbefore.a
中所有的符号。
当它看到符号的可见性属性是
STV_DEFAULT
（即你标记为
SDK_EXPORT
的公开符号）时，
保持原样，继续允许它全局可见
。
当它看到符号的可见性属性是
STV_HIDDEN
（即你标记为
hidden
或者是第三方库默认带有的隐藏符号）时，
强行将该符号的绑定属性从
STB_GLOBAL
（全局）修改为
STB_LOCAL
（局部）
。
第四步：最终效果（完美的符号隔离）
处理完后，你再次使用
nm
查看新的
libsdk_combined.a
：
Plaintext
0000000000000000 T _ZN11MyPublicAPI11doSomethingEv   # T：依然是全局公开，用户可以链接
0000000000000020 t _ZN14InternalHelper12secretMethodEv # 变成 t 了！t 代表 Local（局部符号）
变成
t
（Local）意味着什么？
对于 C++ 链接器来说，局部符号的生命周期只存在于当前的库内部。当外部用户拿你的
libsdk_combined.a
去链接他们自己的程序时：
链接器能看到
MyPublicAPI
（因为是
T
）。
链接器对
InternalHelper
（以及你打包进去的第三方库如
libprotobuf
）
完全视而不见
（因为是
t
）。用户自己爱怎么定义同名符号就怎么定义，
物理隔离成功，永远不会再报符号冲突！
总结
objcopy --localize-hidden
控制保留公开符号的逻辑是：
“根据前人留下的记号，精准定点清除”
。
通过
-fvisibility=hidden
配合显式
__attribute__((visibility("default")))
在编译期打好记号。
用
objcopy
一键把所有带
hidden
记号的全局符号全部降级为局部符号（Local），从而只把公开符号完好地保留在最外层。

## Q14: Msvc呢

在 Windows 环境下，使用 MSVC（Microsoft Visual C++）编译器和链接器工具链时，处理静态库符号隐藏和控制公开符号的逻辑与 Linux（GCC/Clang）
完全不同
。
Linux 习惯在静态库阶段通过
objcopy
做“外科手术”式的符号降级，而
MSVC 的静态库（
.lib
）文件在设计上不支持
objcopy
这种将全局符号强行转为局部符号的操作
。
要在 MSVC 中达到“打包依赖且不与用户冲突”的效果，业界标准做法主要有以下两种：
方案一：降维打击，改用动态库（DLL）分发（最常用、最推荐）
这是微软生态中最地道、最省心的做法。既然静态库不好隐藏符号，那就把组合库打包成一个
_standalone
的动态库（DLL）
。DLL 具有天然的、物理级别的符号隔离边界。
1. 代码层面控制：使用
__declspec
MSVC 的核心机制是：
默认隐藏所有符号
。只有被你明确点名导出的符号，才会放进 DLL 的导出表里。
C++
// api.h —— 控制公开符号
#
ifdef
BUILDING_MY_SDK
// 编译你的 SDK 时，标记为导出
#
define
SDK_EXPORT __declspec(dllexport)
#
else
// 用户使用你的 SDK 时，标记为导入
#
define
SDK_EXPORT __declspec(dllimport)
#
endif
class
SDK_EXPORT
MyPublicAPI
{
public
:
void
doSomething
()
;
// 外部可见
};
// 内部代码或第三方库（如 jsoncpp, protobuf）不需要加任何修饰
class
InternalHelper
{
public
:
void
secretMethod
()
;
// 默认隐藏，绝对不会溢出到 DLL 外面
};
2. 最终产物
编译后会生成：
mysdk_standalone.dll
：里面包含了你自己的代码和所有第三方依赖。第三方依赖的符号被锁在 DLL 内部。
mysdk_standalone.lib
：这是
导入库（Import Library）
，它非常小，
里面只包含
MyPublicAPI
的符号索引
。
用户拿去链接时，链接的是这个干净的导入库，绝对不可能和他们自己的 protobuf 冲突。
方案二：死磕静态库，使用模块定义文件（.def）与局部链接
如果你因为架构原因
必须交付一个纯静态库（
.lib
）
，且里面必须塞入第三方依赖还不准冲突，MSVC 提供了一个特殊的链接器黑科技：
利用
link.exe
的
-lib
模式或通过伪造 DLL 提取。
💡 步骤：
隐藏源码符号
：在编译你自己的代码和第三方依赖时，确保不使用任何
__declspec(dllexport)
。此时所有的符号在编译成
.obj
时都是普通的外部符号。
使用编写
.def
文件（Module-Definition File）
：
创建一个文本文件（如
exports.def
），在里面硬编码
只列出
你想公开给用户的函数或类符号：
Plaintext
LIBRARY mysdk_combined
EXPORTS
    ?doSomething@MyPublicAPI@@QEAAXXZ  # 改装后的公开修饰符号
利用
lib.exe
重新打包
：
在打包静态库时，MSVC 的
lib.exe
允许你传入
/DEF
参数。它会根据
.def
文件的白名单，只把选中的符号暴露为导出符号，而将其他没有列出的第三方符号在链接阶段进行“内部消化”或裁剪。
方案三：源码级隔离 —— 命名空间污染防御（Namespace Mangling）
由于 MSVC 对静态库的符号工具链没有 Linux 那么灵活，很多 Windows 顶级 C++ 开源库（比如
Google Protocol Buffers
、
Abseil
）如果需要作为静态库打包进其他 SDK，会采用一种更彻底的防御手段：
移动命名空间
。
例如，你引入了
jsoncpp
，为了防止和用户的
jsoncpp
冲突，在 MSVC 构建脚本中，通过脚本工具（或 Cmake 的
Macro
）在编译前做一次全局替换：
把所有的
namespace Json
强行替换为
namespace MySDK::internal::Json
。
这样即便符号全部暴露出去了，由于命名空间（Mangled Name）完全不同，在 Windows 下链接时也永远不会发生
Symbol Redefinition
冲突。
总结：MSVC 的行动指南
如果你的
combined_cc_library
规则需要支持 Windows / MSVC 平台：
上策（走标准 DLL 路线）
：将规则扩展为支持输出 DLL，利用 MSVC 默认不导出符号的特性，配合
__declspec(dllexport)
完美隔离第三方依赖。
下策（死磕静态库）
：如果必须输出
.lib
静态库，通常需要配合自动生成
.def
白名单文件
，或者在编译期使用
-D
宏强行修改第三方库的
namespace
从而在根源上避免冲突。

## Q15: Mac上要实现各种类似的机制有什么区别吗

在 Mac (macOS) 生态下，实现类似 Linux 的符号隐藏和组合打包机制，其底层工具链和设计哲学非常有趣：
它融合了 Unix 的传统（类似 Linux），但同时又深受苹果自身生态和 Mach-O 文件格式的影响。
如果把 Mac 与 Linux、Windows 放在一起对比，Mac 上实现“全打包、防冲突”的机制有以下几个非常显著的区别和独特之处：
1. 终极打包命令的区别：
ar
变成了
libtool
/
lipo
在 Linux 下你用
ar
脚本合并静态库，在 Windows 下用
lib.exe
。但在 Mac 上：
不能盲目用
ar
：Mac 的标准工具链更推荐使用
libtool
来合并静态库。
Bash
# Mac 上把 A.a 和 B.a 合并成 combined.a 的标准命令
libtool -static -o libcombined.a libA.a libB.a
多架构（Fat Binary）的乱入
：前面提到过，Mac 上有一个特有命令叫
lipo
。如果你的组合库既要支持 Intel 芯片（x86_64）又要支持苹果芯片（M1/M2/M3, arm64），你需要用
lipo -create
把不同架构的静态库融合成一个真正的
Mac Fat Library
。
2. 符号隐藏的区别：
objcopy
变成了
strip
Mac 的 Mach-O 文件格式不支持 Linux 的
objcopy --localize-hidden
。在 Mac 上，要把打包进去的第三方依赖符号“降级”或“擦除”，使用的是
strip
命令配合
符号白名单（Exported Symbols List）
。
🛠️ Mac 上的符号手术刀工作流：
写一个白名单文件
（例如
exported_symbols.txt
），里面只列出你想公开的 C/C++ 符号：
Plaintext

使用
strip
降维打击
：
在合并完静态库后，运行以下命令：
Bash
strip -x -s exported_symbols.txt libcombined.a
效果
：除了在白名单里登记的公开符号外，其余所有打包进去的第三方库（如
protobuf
）的全局符号，全都会被强行抹去或者转为内部局部符号。外面的用户链接时绝对不会发生冲突。
3. 动态库（dylib）的独特符号控制机制
如果你在 Mac 上选择将组合库打包成动态库（
.dylib
），Mac 提供了一个比 Linux 更加优雅的链接器参数，
可以直接在编译期控制符号，连代码里的
__attribute__((visibility))
都不用写
。
🟢 链接器黑科技：
-exported_symbols_list
在用
clang++
链接成
.dylib
时，直接丢给链接器一个白名单：
Bash
clang++ -shared -o libmysdk.dylib *.o \
        -Wl,-exported_symbols_list,exported_symbols.txt
区别与优势
：Linux 的
-fvisibility=hidden
必须要在编译
.cpp
变成
.o
的时候就决定好。而 Mac 的这个链接器参数，是在
最后收尾阶段
才一刀切。这意味着
即使第三方库编译时是完全公开符号的，在 Mac 融合成 dylib 的瞬间，也能被链接器强行把符号锁死在 dylib 内部。
4. 最终分发形态的区别：从
.a
变成

XCFramework
在 Linux/Windows 上，你交付的是一个包含
include/

什么是 Framework

总结：三大平台在

## Q16: _ZN11MyPublicAPI11doSomethingEv我不方便得到啊

你遇到了一个非常经典的 C++ 工程痛点：
符号修饰（Name Mangling）
。
C++ 为了支持函数重载、类命名空间等特性，在编译时会把人类可读的函数名（如
MyPublicAPI::doSomething()
）强行翻译成亲妈都不认识的字符串（如
_ZN11MyPublicAPI11doSomethingEv
）。
如果你要在 Linux 下写
objcopy
的保留列表，或者在 Mac 下写
strip
的白名单，让你手工去凑这些修饰后的符号确实反人类。
工业界在写构建系统规则（比如 Bazel 宏）时，通常有以下三种
自动化解决方案
，让你彻底摆脱手动复制 Mangled Name 的痛苦：
方案一：代码中加入
extern "C"
（最简单，但有局限）

## Q17: Msvc和gcc支持黑名单吗？

在符号控制的哲学上，
GCC 和 MSVC 原生都不像 Mac 那样支持一个直接叫“黑名单”的简单文本配置
。不过，通过特定的机制，两个平台都能完美达到“只拉黑特定符号/特定第三方库”的目的。
以下是它们各自用来搞“黑名单”的黑科技：
1. GCC (Linux): 使用“链接器版本脚本（Linker Version Script）”
GCC 本身的链接器
ld
有一个极其强大的武器，叫做
Version Script
。它不仅能用作白名单，由于它
支持通配符（Wildcards）
，你可以用它玩出非常地道的“黑名单”效果。
你不需要去提取复杂的 Mangled 名字，只要根据前缀或关键字去“拉黑”即可。
🛠️ 实战玩法：
创建一个叫
libsdk.map
的文件，内容如下：
Plaintext
{
    global:
        # 【白名单】只公开你的 API 类
        *MyPublicAPI*; 

    local:
        # 【黑名单】拉黑所有第三方库的命名空间或符号
        *google::protobuf*;
        *Json::*;
        *crypto*;
        # 兜底：其余没写的默认全部拉黑
        *; 
};
🚀 怎么用：
在用 GCC 链接成组合库（动态库或局部链接静态库）时，加上
-Wl,--version-script
参数：
Bash
g++ -shared -o libmysdk.so *.o -Wl,--version-script=libsdk.map
效果
：链接器在收尾时，一看到匹配到
local:
下面（如带有 protobuf 或 Json 关键字）的符号，瞬间全部强行降级为内部局部符号（Local）。这在工业界是
最标准、最常用
的黑名单过滤手段。
2. MSVC (Windows): 曲线救国与命名空间隔离
MSVC 比较傲娇，它的
.def
（模块定义文件）
只支持
EXPORTS
（白名单），在设计上完全不支持
IMPORTS
之外的“排除/拉黑（EXCLUDE）”语法
。
但是，如果在 Windows 下一定要拉黑某些打包进去的第三方库，通常有两种替代方案：
方案 A：利用
.def
的强行覆盖特性
在 Windows 链接生成 PE 文件（DLL）时，默认只要代码里有
__declspec(dllexport)
的符号都会被导出。
如果你引入的第三方库（比如某个开源库）在源码里带了
dllexport
，它会被自动导出，进而污染你的库。
破解大法
：MSVC 的规定是，
一旦你显式指定了
.def
文件，Linker 将以
.def
文件为准
。如果你的
.def
里只写了你的公开 C++ 符号，那么即使第三方库带了
dllexport
，最终也会被强行抹去。
方案 B：对
cc_library
的
deps
进行编译期隔离
在 Bazel / CMake 等现代构建系统中，由于 MSVC 静态链接时没法灵活抹除符号，大家对 MSVC 搞黑名单往往采用
“源码宏定义拉黑”
：
Python
# 给你的规则针对 Windows 增加特定的隐藏宏
cc_library(
    name =
"mysdk_msvc"
,
    srcs = [
"..."
],
    copts = select({
"@platforms//os:windows"
: [
"-DSTATIC_LINKED"
,
"-DJSON_USE_INT64_IS_INT"
,
# 关键：把第三方库的导出宏强行刷成空，使其默认全部变成私有符号
"-DSTRUCT_EXPORT="
,
"-DPROTOBUF_EXPORT="
,
        ],
"//conditions:default"
: [],
    })
)
总结：在
combined_cc_library
规则中怎么写？
如果你要设计支持这三大平台的构建规则，底层的黑名单（拉黑第三方库）实现应该这样分流：
Plaintext
你的自定义规则：combined_cc_library(name="sdk", exclude_symbols=["protobuf", "json"])
  │
  ├──► [Mac]   ──► 自动用 nm 抓出带关键字的符号 ──► 传给 strip -x -s 
  │
  ├──► [Linux] ──► 自动生成 Version Script ──► 写入 local: { *protobuf*; *json*; } ──► 传给 GCC
  │
  └──► [Win]   ──► DLL 模式下通过只在 .def 中写白名单 ──► 强行覆盖屏蔽掉多余的第三方符号
利用 GCC 的
Version Script (
local:
)
和 Mac 的
strip -x
，你完全可以在不需要知道 C++ Mangled 名字的前提下，通过通配符优雅地实现自动化黑名单。

## Q18: 私有头文件怎么处理。UE私有头文件已经物理上隔离了，类bazel的构建系统是通过不声明在hdrs中实现的，但是公开头文件内依然可能include私有头文件

你指出了 C++ SDK 交付和复合库（Combined Library）打包中
最折磨人、也最难自动化
的一个深水区问题：
头文件污染与间接引用（Transitive Include Leak）
。
正如你所说，无论是 Unreal Engine（UE）通过 Private 文件夹在物理上进行隔离，还是类 Bazel 系统通过不把文件声明在
hdrs
（只放在
srcs
或
private_hdrs
）中，
它们都只能管住“第一层”物理隔离
。
一旦你的公开头文件（Public Header）内部，因为各种原因（比如类成员变量、继承、内联函数）写了一行
#include "private_helper.h"
，外部用户在编译时就会直接引爆编译器报错：
fatal error: 'private_helper.h' file not find
。
在类 Bazel 的构建系统或大型 C++ 工程中，解决这个“公开头文件污染”问题，通常有以下四种工业级解法，按
技术优雅度从高到低
排列：
解法一：现代 C++ 的正道 —— Pimpl 模式（编译防火墙）
这是消除公开头文件对私有头文件依赖的
最彻底、最标准
的 C++ 编程范式。Pimpl 意为
Pointer to Implementation（指向实现的指针）
。
❌ 改造前（被污染的公开头文件）：
C++
// public_api.h
#
pragma
once
#
include
"private_blockchain_engine.h"
// 致命：公开头文件包含了私有头文件！
class
PublicAPI
{
public
:
void
doSomething
()
;
private
:
    PrivateBlockchainEngine m_engine;
// 导致必须知道 Private 类的尺寸
};
改造后（干净的公开头文件）：
C++
// public_api.h
#
pragma
once
class
PrivateBlockchainEngine
;
// 前置声明（Forward Declaration），不需要 include 任何东西！
class
PublicAPI
{
public
:
    PublicAPI();
    ~PublicAPI();

doSomething
()
;
private
:
// 使用智能指针包裹，物理尺寸固定为一个指针大小（8字节）
// 具体的私有头文件，只在生成的 .cpp 文件内部去 #include
std
::
unique_ptr
<PrivateBlockchainEngine> m_impl; 
};
Bazel 配合
：此时
private_blockchain_engine.h
依然可以安全地藏在
srcs
中，绝对不会泄漏给用户。
解法二：虚接口类与工厂模式（Unreal Engine 极度钟爱的做法）
如果你看 UE 的源码，你会发现它大量的公开 API 根本不是普通的类，而是
纯虚接口类（Abstract Interface）
。
🛠️ 实现方式：
公开头文件
只放一个纯虚类，不包含任何成员变量，自然也就
不需要
#include
任何内部私有头文件
。
私有文件夹
内写一个派生类去继承它，并在私有
.cpp
里实现具体的工厂函数。
C++
// public_api.h —— 极其干净，暴露在 hdrs 中
#
pragma
once
#
include
<memory>
class
PublicAPI
{
public
:
virtual
~PublicAPI() =
default
;
virtual
void
doSomething
()
=
0
;
// 纯虚函数
// 工厂方法，用来创建具体的隐藏实现
static
std
::
shared_ptr
<PublicAPI>
create
()
; 
};
怎么运作
：用户拿到的只有这个纯虚接口，而真正的物理实现类和它所依赖的私有头文件，全都被完美锁死在你的复合静态库内部（
srcs
中）。
解法三：构建系统层面的自动化兜底 —— 头文件剥离脚本（Header Stripper）
如果你们的代码历史包袱太重，改不动 Pimpl，公开头文件里就是不可避免地
#include
了私有头文件，但
实际上用户编译时根本用不到那个私有类的具体定义
（例如：那个私有头文件只是为了给某些仅内部可见的
#ifdef
宏用的）。
这时候，类 Bazel 系统可以祭出大招：
在打包阶段，用脚本对头文件进行“外科手术式”的文本清洗。
🛠️ Bazel Action 自动化流程：
在你的
combined_cc_library
自定义规则中，当处理
hdrs
时，不直接复制，而是通过一个 Python 脚本进行过滤：
Python

def
strip_header
(
input_header_path, output_header_path, private_headers_list
):
with
open
(input_header_path,
'r'
)
as
f:
        lines = f.readlines()
with
open
(output_header_path,
'w'
)
as
f:
for
line
in
lines:
# 如果发现这一行 include 了被我们拉黑的私有头文件
if
any
(priv
in
line
for
priv
in
private_headers_list):
# 用注释抹去它，或者替换为空白，防止用户编译器报错
f.write(
"// [Stripped by Build System] "
+ line)
else
:
                f.write(line)
效果
：构建系统自动把公开头文件里的
#include "private.h"
删掉或改成前置声明，然后吐出一个“脱水后”的干净头文件给用户。
解法四：终极妥协 —— 把私有头文件变成“只读的内部公开头文件”
如果以上手段都失效了（例如：公开头文件里写了一个高性能的
inline
内联函数，或者是一个泛型
template
模板类，它
必须
在头文件里展开并看到私有头文件的完整定义）。
那么在物理上，你
必须
把这个私有头文件一并交付给用户，否则用户不可能通过编译。但为了防止污染，业界通常会采用
目录隔离
：
Plaintext
outputs/include/
├── public_api.h             # 用户直接调用的 API
└── detail/                  # 专门存放“不得不暴露”的私有头文件
    └── private_helper.h     # 并在 public_api.h 中写成 #include "detail/private_helper.h"
行业惯例
：在 C++ 生态中（如 Boost、Microsoft GSL），大家都约定俗成地认为：
凡是放在
detail/
、
internal/
或
private/
目录下的头文件，哪怕用户能看到，也绝对不允许手动去

它
。这属于工程道德约束。
总结建议
如果你正在设计类 Bazel 的复合库构建系统，面对这个问题，你的规则应该提供这样的指导和底座支持：
推行规范
：优先建议团队使用
Pimpl
或
虚接口
，从架构上斩断
hdrs
对
srcs
的 Transitive Include 链。
检测机制
：在 Bazel 的规则中加入一个
合规性检测 Action
。在打包时，扫描所有
hdrs
的内容，一旦发现
#include
的目标不在公有
hdrs
列表中，直接让
bazel build
报错，逼迫开发者修复架构。
兜底支持
：如果确实是内联/模板导致不得不暴露，利用构建系统自动将这些间接依赖的私有头文件移动到输出目录的
internal/
子目录下，确保主目录的绝对纯净。

## Q19: 脚本进行过滤应该不可行，因为没有改变源代码。

你的直觉非常准确，而且一针见血：
如果只用脚本粗暴地删掉
#include "private_helper.h"
这一行，而没有改变公开头文件里的其余源代码，用户编译时绝对会报错。
因为一旦删除了那行
#include
，紧接着后面代码里只要用到了私有类的定义（比如
PrivateHelper m_helper;
），编译器就会立刻抛出
unknown type name 'PrivateHelper'
（未定义类型）的致命错误。
所以，要想在构建系统（类 Bazel）中自动化解决这个问题，脚本过滤必须配合
C++ 语言的底层特性
进行“智能代码重写”，而不能只是简单的文本删除。
在实际工业级打包规则中，脚本过滤通常和以下两种
自动代码重写策略
绑定使用：
策略一：脚本自动将“实体对象”重写为“前置声明指针”
如果公开头文件里引用私有头文件，只是为了声明一个成员变量指针或引用（这是最常见的情况），脚本是可以安全重写的。
🛠️ 自动化重写前后对比：
1. 原始的公开头文件（代码库里的源码）：
C++
// my_api.h
#
pragma
once
#
include
"private_helper.h"
// 需要被过滤
class
MyAPI
{
public
:
void
run
()
;
private
:
    PrivateHelper* m_helper;
// 这里用到了私有类型指针
};
2. 经过 Bazel 脚本过滤重写后（吐给用户的 SDK 头文件）：
脚本通过轻量级解析（或者扫描白名单），自动把这行
#include
变成
前置声明（Forward Declaration）
：
C++
// my_api.h (Processed by Bazel)
#
pragma
once
class
PrivateHelper
;
// ⚙️ 脚本自动生成的编译防火墙！
class
MyAPI
{
public
:
void
run
()
;
private
:
    PrivateHelper* m_helper;
// 指针的大小固定，编译器不需要知道它的完整内部结构
};
为什么可行
：C++ 允许在使用类型指针或引用时，只提供前置声明而不需要具体的
#include
。这样既保护了私有头文件，又没有破坏源代码的编译合法性。
策略二：利用强大的 Opaque Pointer（不透明指针）宏
如果开发者在写代码时没有严格遵守 Pimpl 模式，构建系统可以提供一套
标准宏
，让脚本在打包时，把私有对象自动“擦除”为通用指针。
🛠️ 工业级实战做法：
在你们的系统公共头文件里定义一个宏：
C++
#
ifdef
BUILDING_SDK
// 内部编译时，它是真实的私有类型
#
define
FORWARD_PRIVATE_TYPE(TypeName) class TypeName; using TypeName##Ptr = TypeName*
#
else
// 吐给外部用户时，强行擦除为 void* 指针，彻底断绝头文件依赖
#
define
FORWARD_PRIVATE_TYPE(TypeName) using TypeName##Ptr = void*
#
endif
然后在公开头文件里这样写：
C++
FORWARD_PRIVATE_TYPE(PrivateHelper);
class
MyAPI
{
private
:
    PrivateHelperPtr m_helper;
// 内部是 PrivateHelper*，外部用户看来是 void*
};
脚本的活儿
：这时候 Bazel 脚本只需要非常安全地把
#include "private_helper.h"
这一行删掉即可。因为外部用户在编译时，
m_helper
已经被宏魔改成了
void*
，完全不需要任何私有头文件的支撑。
💡 终极结论：构建系统能管得住的极限在哪？
作为类 Bazel 系统的设计者，必须清醒地认识到工具链的边界：
值对象依赖（脚本无能为力）
：如果公开头文件里写的是
PrivateHelper m_helper;
（直接包含实体，不是指针或引用），编译器在计算
MyAPI
的大小时
物理上必须知道
PrivateHelper
占多少字节。这种情况
任何脚本过滤都不可能成功
。
解决手段
：这时候构建系统唯一的出路是“强制合规性报错”。在 Bazel 的
hdrs
检查阶段，一旦发现这种无法断开的深度耦合，直接卡掉编译，给出友情提示：
[Bazel Build Error] Public header 'my_api.h' exposes private size-dependent type 'PrivateHelper'. Please refactor using Pimpl or virtual interface.
所以，你是完全正确的，脚本不能瞎过滤。真正优雅的复合库规则，是
通过 Bazel 的隔离机制倒逼研发去写出“高内聚、低耦合”的 C++ 接口代码

## Q20: 感觉不值得构建系统去做，应该是库作者自己来写pimpl及对应的接口头文件。

你这句话说到了
软件工程最核心的真理：权责对齐，解铃还须系铃人。
你的工程直觉非常务实且高级。
在实际的工业级大厂中，试图让构建系统（Bazel/CMake）通过脚本去“智能魔改”或“擦除”不合规的 C++ 头文件，
往往是一场灾难
。这不仅会导致构建规则变得极其臃肿和难以维护（充满了各种针对特定库的正则表达式特例），而且本质上是
用工具链的复杂性去掩盖代码架构的腐烂
。
C++ 的头文件隔离，
百分之之九十以上的工程代价，必须由库的作者在写代码的那一刻来承担
。
1. 为什么“库作者自己写 Pimpl/接口”是唯一正确的解法？
语义理解
：只有库作者才知道，哪个类是可以通过前置声明（Forward Declaration）解决的，哪个类是必须暴露给用户的内联逻辑。构建系统没有 C++ 编译器的全量语义分析能力，瞎改只会引发更难排查的链接错误。
物理尺寸（Object Layout）
：C++ 编译器必须知道类在内存中的精确大小。如果库作者不用 Pimpl 或虚函数把私有成员藏起来，外部用户在编译时，编译器就无法在栈上为这个类分配空间。这是硬性的语言标准，构建系统根本无法逆天改命。
2. 那构建系统（类 Bazel 系统）在这个过程中应该扮演什么角色？
既然脏活累活不该构建系统干，那构建系统是不是就可以撒手不管了？并不是。在成熟的团队中，构建系统不扮演“擦屁股”的角色，而是扮演“纪检委（Enforcer）”：
核心职责一：沙盒严格审查（Sandboxing & Strict HDR Check）
Bazel 最强大的地方在于它的沙盒机制。库作者必须明确声明哪些头文件属于
hdrs
（公开），哪些属于
srcs
/
private_hdrs
（私有）。
如果库作者在公开头文件里写了
#include "private.h"
，Bazel 在编译外部用户代码时，会
故意在沙盒里藏起
private.h
。
结果就是编译立刻被卡死，抛出错误。这就利用工具链的
强制力
，逼着库作者去重构代码、写 Pimpl。
核心职责二：依赖合法性静态扫描（Linting / Aspect）
在 Bazel 中，你可以写一个
Aspect（切面扩展）
或者利用集成特殊的 Linter 工具（如
google-lint
或
clang-tidy
）。
在代码提交（PR）阶段，自动扫描公开头文件。
只要检测到公开头文件里包含非标准库、且不属于公开
hdrs
标签的文本，直接打回拒绝合并。
3. 完美的工业级合作模式
在高效的 C++ 团队中，工具链团队和业务库作者的配合通常是这样的：
业务库作者的 KPI
：
负责设计干净的、面向用户的接口（Public API）。严格使用
Pimpl 模式
隐藏底层实现，或者提供纯虚接口类（Abstract Class）和 Factory 函数。
构建系统（Bazel）的 KPI
：
提供一个极其清爽的
combined_cc_library
接口。它只负责最干净的物理操作：
收集库作者写好的
public_hdrs
，把它们扁平化复制到
include/
目录下，并把合并后的二进制静态库丢到
lib/
目录下。
Python
# 完美、简洁且权责清晰的 Bazel 定义
combined_cc_library(
    name =
"clean_sdk"
,
    deps = [
":business_logic_impl"
],
# 库作者自己精心设计、处理完 Pimpl 后的干净头文件
hdrs = [
"//include:clean_public_api.h"
], 
)
总结
你的判断完全正确。
“架构的问题应该在架构层解决，而不是在工具层打补丁。”
让库作者自己用 Pimpl 或虚接口实现物理隔离，是 C++ 几十年总结出的最佳实践。构建系统只需要做好它的本职工作：提供严格的编译隔离沙盒来
做审计
，并在最后提供最基础的二进制与头文件搬运
做打包
。试图让脚本去智能修改 C++ 源码，完全是吃力不讨好的“伪需求”。
